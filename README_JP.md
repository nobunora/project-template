# Project Template

[English](README.md)

人間、AIコーディングエージェント、Codex系のリポジトリエージェントを組み合わせた開発を、根拠ベースで規律正しく進めるための、言語非依存プロジェクトテンプレートです。

このリポジトリは単なるディレクトリ雛形ではありません。要件を明示的な契約として残し、実装前に実リポジトリとの整合性を確認し、検索や静的解析は可能な限り決定論的ツールへ任せ、変更範囲を限定し、重要な変更は独立レビューまで行うための「開発制御の仕組み」をまとめています。

## 目的

このテンプレートは、人間・AI支援開発の双方で起こりやすい次の失敗を減らすことを目的としています。

- リポジトリを大量に読み過ぎて、重要な文脈が埋もれる;
- 仕様、互換性、セキュリティ、外部契約を推測で補う;
- 仕様が実際のソース構造と一致するか確認する前に実装を始める;
- 機能追加、リファクタリング、整形、掃除を一つの変更へ混在させる;
- テストが通っただけで、仕様どおりであると判断する;
- 実装したエージェント自身の前提だけでレビューを完結させる;
- 本来は検索や静的解析で済む処理に高価なLLM/Codexのコンテキストを使う;
- 要件や判断根拠がチャット履歴にしか残らず、後から追えなくなる。

中心原則は、**根拠を先に集め、必要最小限の文脈を読み、契約を明示し、変更範囲を限定し、結果を再検証可能にすること**です。

## 全体の実行フロー

```text
要求 / アイデア
    |
    v
明示的な仕様書
    |
    v
仕様契約ゲート
    |
    v
リポジトリレビュー（読み取り専用）
    |
    +---- 矛盾 / 根拠不足 ----> 仕様修正
    |
    v
検証済み実装契約
    |
    v
範囲を限定した実装
    |
    v
決定論的チェック + テスト + 静的解析
    |
    v
実装レビュー
    |
    +---- 高リスク変更 ----> 独立ブラインドレビュー
    |
    v
根拠を記録 -> マージ / リリース
```

### 1. 最小限の文脈から始める

最初に `AGENTS.md`、次に `docs/00_index.md` を読みます。その後、全ファイルを読むのではなく、メタデータ、`rg`、シンボル検索、必要行だけの読み取りを優先します。

これにより、人間の探索コストだけでなく、LLM/Codexのコンテキスト・トークン消費も抑えられます。

### 2. 要件を仕様契約へ変換する

非自明な変更では、実装方法に依存しない仕様を `docs/specs/` に置き、少なくとも次を明示します。

- Goal（目的）;
- Scope（対象範囲）;
- Non-goals（対象外）;
- Requirements / Invariants（要件・不変条件）;
- 影響するインターフェースや契約;
- Acceptance Criteria（受入条件）;
- Validation（検証方法）;
- 必要に応じてリスクとロールバック条件。

要件の正本をチャット履歴ではなくGitHubへ残すことが狙いです。

### 3. リポジトリ実行前に仕様をゲートする

仕様PRをリポジトリ検証へ進められる状態にしたら、`codex-ready` ラベルを付けます。

`.github/workflows/spec-ready-gate.yml` は、仕様ファイルが変更されていることと、必要な契約セクションが揃っていることを決定論的に検証します。このゲート自体はモデルを呼び出しません。

### 4. 実装前に実リポジトリをレビューする

最初のリポジトリエージェント処理には `.codex/repository-review.md` を使用します。

エージェントは実際のソース、インターフェース、実行経路、テスト、設定、永続化・プロトコル境界、ビルド経路を確認しますが、**本番ソースは変更しません**。結果は次のいずれかです。

- `validated`;
- `spec-change-required`;
- `blocked`。

仕様と実装現実が矛盾する場合、実装側で勝手に意味を変えず、仕様判断へ差し戻します。

### 5. 検証済み契約だけを実装する

リポジトリレビューが `validated` になった後、`.codex/implementation.md` を使用します。

実装では次を要求します。

- レビュー可能な最小差分にする;
- 無関係な挙動や公開契約を保持する;
- 変更箇所に近いチェックから先に実行する;
- リスクに応じて広いチェックへ拡張する;
- 実リポジトリが承認済み仕様と重大に矛盾したら停止する;
- 実行したコマンド、結果、残存リスクを記録する。

### 6. リポジトリ探索を決定論的ツールへ任せる

`scripts/repo_query.py` は、安定したJSON出力を返すリポジトリ検索CLIです。

```bash
python3 scripts/repo_query.py doctor
python3 scripts/repo_query.py index
python3 scripts/repo_query.py files adc
python3 scripts/repo_query.py text ADC_TIMEOUT
python3 scripts/repo_query.py symbol process_adc
python3 scripts/repo_query.py refs process_adc
python3 scripts/repo_query.py callers process_adc
python3 scripts/repo_query.py callees control_loop
python3 scripts/repo_query.py tests process_adc
python3 scripts/repo_query.py changed
```

内部では次を使います。

- Git と ripgrep: 安価な字句検索;
- Universal Ctags: 言語非依存のシンボル定義検索;
- clangd + `compile_commands.json`: C/C++の意味的な参照・呼出階層検索。

字句検索結果と意味解析結果は明確に区別されます。また、ファイル全文ではなく、位置情報と短い一致行を返します。

**メリット:** LLMへ巨大なソースを読ませる前に必要箇所を限定でき、探索コスト、再現性、コンテキスト消費を改善できます。

### 7. 静的解析を決定論的に実行する

`scripts/analyze.py` は、clang-tidyをラップしたC/C++向け静的解析ツールです。

```bash
python3 scripts/analyze.py doctor
python3 scripts/analyze.py fast
python3 scripts/analyze.py normal
python3 scripts/analyze.py deep
python3 scripts/analyze.py file src/example.cpp
```

解析コストと対象範囲を明確に分けています。

- `fast` — 変更されたC/C++翻訳単位のみ;
- `normal` — 変更された翻訳単位。ヘッダ変更時は保守的に範囲を拡大;
- `deep` — `compile_commands.json` 内の全翻訳単位;
- `file` — 指定した1翻訳単位。

診断はJSONへ正規化され、元のclang-tidyログも保存されます。既知問題を扱うbaselineは明示的に管理され、終了コードも自動化向けに定義されています。

C/C++では、`repo_query.py` の意味解析と `analyze.py` が同じ `compile_commands.json` を正本として使うため、clangd用とclang-tidy用のビルド設定が別々にずれることを防げます。

### 8. 実装と独立判断を分離する

`docs/15_model_orchestration.md` では、AI作業を次のような役割へ分けます。

- Architect / Adjudicator（設計・裁定）;
- Lead Repository Agent（主担当リポジトリエージェント）;
- Delegated Investigator / Implementer（限定調査・実装担当）;
- Blind Reviewer（独立レビュー担当）。

高性能な推論モデルは、アーキテクチャ、矛盾解消、裁定、最終判断に使い、検索や反復確認は安価なモデルや決定論的ツールへ任せます。

高リスク変更では `docs/16_blind_review_protocol.md` に従い、独立レビュアーが**一次レビューの結論を先に見ずに**、仕様とソースから挙動を再構築して確認します。

**メリット:** 同じ前提を共有したまま全エージェントが同じ誤りをする相関ミス、確認バイアス、自己レビューの見落としを減らせます。

### 9. 根拠を記録する

`docs/08_report_template.md`、`docs/implementation/`、`docs/records/` を使って次を残します。

- 変更ファイルと理由;
- 実行したコマンド;
- 実行結果;
- 検証できなかった点;
- 人間が確認すべき点;
- 残存リスク;
- マイルストーンと次の作業。

実行していないテストやコマンドを「成功した」と記録してはいけません。

## 基本的な設計・実装ルール

文書全体では、次のルールが一貫して適用されます。

- 一つの業務上の意味には、一つの明確な所有者を置く;
- コンポーネントの責務を狭くし、境界を明示する;
- 依存方向をドメイン側へ意図的に向ける;
- 公開API、永続化フィールド、環境変数キー、外部連携フィールドは契約として扱う;
- 不明な挙動を推測せず検証する;
- 機能追加、リファクタリング、整形、移行を理由なく混在させない;
- 必要に応じ、正常系、異常系、境界値、回帰、互換性、外部障害をテストする;
- 危険な入力は高コスト処理や副作用の前に検証する;
- 例外の握り潰し、一時的なバイパス、デバッグコード、不必要な依存追加を残さない;
- テスト成功は証拠であって、仕様準拠の完全な証明ではない;
- 「問題なし」のレビューでも、何を確認し何が未検証かを記録する。

## 標準スクリプト契約

このテンプレートを使う各プロジェクトでは、実際の言語・ビルドシステムに応じて、次の安定した意図へコマンドを割り当てます。

| スクリプト | 意図 |
| --- | --- |
| `doctor` | 環境確認 |
| `check` | 軽量なローカル検証 |
| `typecheck` | 型・静的チェック |
| `test` | 単体・統合テスト |
| `build` | 本番ビルド・パッケージ |
| `refactor:check` | 直列実行するリファクタ用ゲート |
| `release:check` | 直列実行するリリース前ゲート |

これは「契約上の名前」であり、全言語で同じ実装を使うことを要求するものではありません。

## クイックスタート

1. 新規プロジェクトのベースとしてこのリポジトリをコピーします。
2. `AGENTS.md` を読みます。
3. `docs/00_index.md` を読み、作業に関係するカテゴリだけを開きます。
4. 標準スクリプト契約を、そのプロジェクトの実ツールチェーンへ割り当てます。
5. リポジトリ検索を使う場合、`docs/17_repo_index_and_query.md` の依存関係を導入し、次を実行します。

   ```bash
   python3 scripts/repo_query.py doctor
   ```

6. C/C++の意味解析や静的解析を使う場合、実際のビルド設定から正確な `compile_commands.json` を生成します。
7. 非自明な変更では、実装より先に仕様を作成し、`docs/19_chat_github_codex_workflow.md` の Chat -> GitHub -> Codex フローを使います。
8. マージやリリース前に、実行コマンド、根拠、リスク、未解決事項を記録します。

## 得られるメリット

このテンプレートを継続的に使うことで、実務上は次の効果が期待できます。

- **コンテキスト・トークン消費の削減:** 全文読みではなく限定検索と短いJSON根拠を使える。
- **仕様ドリフトの抑制:** 要件をGitHub上の契約として残し、重大な矛盾があれば実装を停止できる。
- **再現性の向上:** 検索、静的解析、テスト、ゲートが決定論的で再実行できる。
- **AIコスト配分の改善:** 高性能モデルを設計・裁定へ集中し、検索や反復確認をオフロードできる。
- **レビュー品質の向上:** 変更行だけでなく影響経路を確認し、必要なら独立ブラインドレビューを追加できる。
- **安全なリファクタ・リリース:** 現状挙動を保護してから構造を変え、リスクに応じて検証範囲を広げられる。
- **保守しやすい構造:** 一意味一所有者、明示的な依存方向、状態・失敗契約により変更影響が予測しやすくなる。
- **引継ぎ・監査性の向上:** 仕様、実装記録、コマンド、結果、残存リスクがチャット終了後もGitHubに残る。

## 推奨する読み順

1. `AGENTS.md`
2. `docs/00_index.md`
3. 作業に必要な core / ops / dev 文書だけ
4. 仕様から実装へ進める場合は `docs/19_chat_github_codex_workflow.md`
5. 決定論的なローカル解析が必要なら `docs/17_repo_index_and_query.md` と `docs/18_static_analysis.md`
6. 複雑・高リスクな複数エージェント作業なら `docs/15_model_orchestration.md` と `docs/16_blind_review_protocol.md`

最終的な正本は常に実際のソースツリーです。索引、生成された解析結果、エージェントの要約、過去レビューの結論は補助的な根拠であり、実リポジトリや承認済み仕様を暗黙に置き換えてはいけません。
