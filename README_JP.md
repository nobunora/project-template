# Project Template

[English](README.md)

人間、AIコーディングエージェント、Codex系のリポジトリエージェントのどれが作業しても、コードベースが成長した後まで**読みやすく、変更しやすく、レビューしやすい状態を保つ**ための、言語非依存プロジェクトテンプレートです。

このリポジトリは単なるディレクトリ雛形ではありません。**既存コードの意図を理解してから変更する、契約を守る、必要最小限の変更にする、型と名前で意味を表現する、責務を局所化する、根拠で検証する、判断を記録する**という開発規律を文書・テンプレート・スクリプトとしてまとめています。

Codexや複数AIを使った高度なワークフローも、その上に構築されています。AIに設計を丸投げすることが目的ではなく、良いソフトウェア設計の制約を明文化し、人間とAIが同じルールで作業できるようにすることが目的です。

## このテンプレートが解決しようとしている問題

大きく二種類の失敗を減らします。

### コード品質上の失敗

- 既存コードがなぜその形になっているか確認せずに変更する;
- 局所変更で済む問題を広範囲に書き換える;
- 機能追加、リファクタリング、整形、移行、掃除を一つの差分に混ぜる;
- 一つの業務ルールを複数モジュール、アダプタ、エントリポイントへ重複実装する;
- `manager`、`helper`、`data`、`process` のような汎用名で意図を隠す;
- 明示的な意味を持つ型の代わりに、広い辞書、DB行、フレームワークオブジェクト、曖昧なデータを境界越しに渡す;
- 強い理由なしに `any` や未型付けの逃げ道を使う;
- 公開API、永続化フィールド、設定キー、単位、null可否、失敗時挙動などの契約を偶発的に変える;
- booleanフラグや暗黙状態を増やし、状態遷移を追えなくする;
- 将来使うかもしれないという理由だけで抽象化や層を増やす;
- 例外を握りつぶす、一時バイパスを残す、必要性の薄い依存を増やす;
- 今は動くが、次の変更で大規模リファクタリングを必要とする構造を作る。

### 人間・AI開発フロー上の失敗

- リポジトリを大量に読み過ぎて重要な文脈を失う;
- 仕様、互換性、セキュリティ、外部契約を推測で補う;
- 仕様が実際のリポジトリ構造と一致するか確認する前に実装する;
- テストが通っただけで仕様どおりだと判断する;
- 実装したエージェント自身の前提だけでレビューを完結させる;
- 検索や反復解析のような決定論的処理に高価なモデル能力を消費する;
- 要件、根拠、判断、リスクをチャット履歴だけに残す。

中心ルールは次です。

> **まず理解する。既存の意図と契約を守る。最小の一貫した変更をする。意味を明示する。根拠で検証する。**

## コアとなるコーディング思想

### 1. 既存コードの意図を理解してから変更する

最初にメタデータと限定検索を使い、対象の責務を持つコンポーネント、呼び出し元、利用側、状態、テスト、外部契約を確認します。

見慣れない構造を「無駄」と決めつけません。名前、処理順序、状態遷移、互換ラッパー、永続化形式、エラー処理には、過去の要件や制約が埋め込まれている可能性があります。

既存設計を変更すること自体が目的でない限り、変更は現在の設計へ合わせます。

**得られる効果:** 意図を理解せずに作り直すことによる回帰や仕様破壊を減らせます。

### 2. 本当に必要な最小変更を優先する

機能追加、リファクタリング、整形、移行、無関係な掃除は可能な限り分離します。

良い差分は、次を簡単に説明できる状態です。

- 何を変えたか;
- なぜ変えたか;
- 何を意図的に変えていないか;
- どの挙動・契約が影響を受けるか;
- 何で検証したか。

リファクタリングでは、まず現在の挙動をテストや特性テストで固定します。可能なら、構造移動と挙動変更は別段階にします。

**得られる効果:** レビュー範囲、ロールバック範囲、回帰リスクを小さくできます。

### 3. 将来の変更が局所化するように設計する

このテンプレートは「今後一切リファクタリングしなくてよい」とは主張していません。狙いは、**大規模リファクタリングが必要になる構造を最初から避け、将来の変更箇所を予測可能にすること**です。

中心原則は **One Meaning, One Owner（一つの意味に一つの所有者）** です。

業務ルール、状態遷移、フォールバック順序、計算、検証ポリシー、表示上の意味などは、一つの権威ある実装に集約します。

各コンポーネントには次を求めます。

- 変更理由が狭い;
- 何を所有し、何を所有しないかが明確;
- 依存方向が意図的;
- 境界契約が小さい;
- 可変状態の所有者が明確;
- 失敗時の挙動が定義されている。

アダプタは外部形式を変換しても、業務ルールを再実装しません。エントリポイントは調停しても、別のポリシー所有者になりません。互換レイヤは過去契約を維持しても、現在の実装へ委譲し、二重実装を残し続けません。

**得られる効果:** 新しい要求が入ったときに、リポジトリ全体ではなく「ここを直せばよい」という場所が明確になります。

### 4. 型と契約に意味を持たせる

コンポーネント境界では、単にデータを運ぶだけでなく意味を表現します。

言語が対応している場合は、広い辞書、DB行、フレームワークのrequest、汎用payloadを深い層までそのまま渡すより、意味を持つ明示的な型・モデルを優先します。

重要な境界では次を明示します。

- 入力・出力の意味上の型;
- 単位と時間基準;
- null可否と欠損時の挙動;
- どこが検証責任を持つか;
- エラー分類;
- 再試行可能性と冪等性;
- 順序制約;
- 互換性・バージョン条件。

強い理由なしに `any` や未型付けの逃げ道は使いません。公開API、DBフィールド、環境変数キー、プロトコルフィールド、連携名は「見た目」ではなく契約として扱い、スタイル上の理由だけで変更しません。

このテンプレートでいう「型を固定する」方向性は、**データの形と意味を意図的に固定し、コンポーネント間で暗黙に変化させない**という意味です。

**得られる効果:** 無効状態、境界の曖昧さ、型ずれを減らし、人間・IDE・静的解析・AIの全てが理解しやすくなります。

### 5. 人間が意図を読み取れるコードを書く

名前はドメイン上の意味、目的、状態、必要なら単位を表します。プロジェクトで既に使われている語彙を優先します。

責務を隠す場合は、`data`、`result`、`item`、`value`、`manager`、`service`、`helper`、`util`、`process`、`execute`、`handle` などの汎用名を避けます。

コメントは「何をしているか」ではなく、**なぜそうするか、どの制約があるか、どの不変条件があるか、どのプロトコル・ハードウェア上の事情があるか**を説明します。

長いコメントがなければ処理内容を理解できないなら、まず関数、責務境界、命名を改善できないか検討します。

**得られる効果:** 半年後の人間や別AIが、リポジトリ全体を読み直さなくても変更箇所を見つけやすくなります。

### 6. 状態と失敗を明示する

可変状態には必ず所有者を設けます。誰が書けるか、誰が読めるか、同時書き込みがあるか、古い状態をどう判定するか、部分更新をどう防ぐかを定義します。

相互依存するbooleanが増えたら、フラグを追加し続けるのではなく、状態機械やdiscriminated unionを検討します。reset、初期化、cleanup、save、preview、progress、workflowの順序が挙動に関わる場合は、その順序を明示的に保ちます。

失敗を空配列や0へ隠さず、ドメイン仕様として明示的に許可されている場合だけフォールバックします。広い例外catchで失敗を握りつぶしません。危険な入力は、高価な処理や副作用の前に検証します。

**得られる効果:** デバッグ、レビュー、障害復旧時に実際の状態遷移を再構築しやすくなります。

### 7. 抽象化・依存追加は実在する理由があるときだけ行う

抽象化は、実際の重複を消す、実在する境界を明確にする、既存設計に一致する場合に追加します。「将来使うかもしれない」だけでは層を増やしません。

外部依存も、必要性、保守状況、セキュリティ、ライセンス、実行時/バンドル影響、テスト容易性を確認します。既存ツールや標準ライブラリで十分ならそちらを優先します。

**得られる効果:** 将来の柔軟性という名目で保守負債を作ることを防ぎます。

### 8. テスト・静的解析は「根拠」であり「証明」ではない

必要に応じて、正常系、異常系、境界値、空入力、欠損/null、回帰、既存データ互換、外部障害、timeout/retry、権限を確認します。

まず変更箇所に近いチェックを実行し、リスクに応じて広いテストへ拡大します。実行していないコマンドを「通った」と報告してはいけません。実行できない場合は、理由と、人間が実行すべき正確なコマンドを記録します。

テストが通っても、アーキテクチャ品質や仕様準拠まで証明されたことにはなりません。挙動の根拠と、責務・依存・所有権などアーキテクチャ上の根拠を分けて考えます。

**得られる効果:** 検証が再現可能で、誇張されず、変更リスクに比例したものになります。

### リポジトリを読むときの規律

最初に `AGENTS.md`、次に `docs/00_index.md` を読みます。その後は `git status`、浅いディレクトリ一覧、`rg`、シンボル検索、必要行だけの読み取りを優先します。

`docs/core/`、`docs/ops/`、`docs/dev/` の索引は、全ルールを毎回読むのではなく、現在の作業に必要な文書だけを開くためにあります。

### 実装前の仕様契約

非自明な変更では `docs/specs/SPEC_TEMPLATE.md` を使い、次を明示します。

- Goal;
- Scope;
- Non-goals;
- Requirements / Invariants;
- Affected Interfaces / Contracts;
- Acceptance Criteria;
- Validation;
- Risks / Rollback;
- Open Questions。

仕様書は「何が真であるべきか」を定義します。実リポジトリとの互換性は、リポジトリレビューが確認するまで断定しません。

### 決定論的な仕様ゲート

仕様PRがリポジトリレビューへ進める状態になったら `codex-ready` ラベルを付けられます。`.github/workflows/spec-ready-gate.yml` が、仕様ファイルの変更と必須セクションの存在を決定論的に検証します。このゲート自体はモデルを呼びません。

### 実装前の読み取り専用リポジトリレビュー

`.codex/repository-review.md` では、対象ソース、インターフェース、実行経路、テスト、設定、永続化/プロトコル境界、ビルド経路を調べますが、本番コードは変更しません。

結果は必ず次のどれかです。

- `validated`;
- `spec-change-required`;
- `blocked`。

リポジトリレビュー側が仕様を勝手に書き換えてはいけません。

### 検証後の限定実装

`.codex/implementation.md` では、リポジトリ前提を再確認し、最小のレビュー可能な実装計画を作り、無関係な挙動や契約を保ち、近いチェックから実行し、必要に応じて検証範囲を広げます。

未承認の公開API変更や重大な仕様矛盾が必要になった時点で実装を停止し、仕様判断へ戻します。

## 決定論的リポジトリ探索

`scripts/repo_query.py` は安定したJSON出力を返す検索・索引レイヤです。

```bash
python3 scripts/repo_query.py doctor
python3 scripts/repo_query.py index
python3 scripts/repo_query.py files adc
python3 scripts/repo_query.py text ADC_TIMEOUT
python3 scripts/repo_query.py symbol process_adc
python3 scripts/repo_query.py refs process_adc
python3 scripts/repo_query.py callers process_adc
python3 scripts/repo_query.py callees control_loop
python3 scripts/repo_query.py tests process_adc
python3 scripts/repo_query.py changed
```

内部では次を利用します。

- Git / ripgrep: 安価な字句検索;
- Universal Ctags: 言語非依存の定義検索;
- clangd + `compile_commands.json`: C/C++の意味的な参照・call hierarchy。

字句検索と意味解析の結果は明示的に区別されます。意味解析に失敗したとき、勝手に字句検索結果を「意味解析結果」として代用しません。全文ではなく位置と短い一致行を返します。

**メリット:** 人間やAIが巨大なソースを読む前に対象を絞れ、探索コスト、再現性、コンテキスト効率を改善できます。

## 決定論的静的解析

`scripts/analyze.py` はC/C++向けのclang-tidy実行・正規化レイヤです。

```bash
python3 scripts/analyze.py doctor
python3 scripts/analyze.py fast
python3 scripts/analyze.py normal
python3 scripts/analyze.py deep
python3 scripts/analyze.py file src/example.cpp
```

対象範囲を分けています。

- `fast` — 変更されたC/C++翻訳単位;
- `normal` — 変更翻訳単位。ヘッダ変更時は保守的に拡張;
- `deep` — `compile_commands.json` の全翻訳単位;
- `file` — 指定した1翻訳単位。

診断はJSONへ正規化し、rawログも保存します。baselineは明示的に管理し、終了コードで「問題検出」と「環境/ツール失敗」を区別します。

C/C++では `repo_query.py` と `analyze.py` が同じ `compile_commands.json` を正本として使うため、検索側と静的解析側でビルド条件が別々にずれることを防ぎます。

## 複数AIと独立レビュー

`docs/15_model_orchestration.md` では責任を次のように分けます。

- **Architect / Adjudicator** — 要件、設計、矛盾解消、最終判断;
- **Lead Repository Agent** — 実リポジトリ調査、実装、検証;
- **Delegated Investigator / Implementer** — 限定検索、機械的/局所作業;
- **Blind Reviewer** — 先行結論を引き継がない独立レビュー。

正しさへ大きく影響する判断には強い推論能力を使い、反復検索や限定調査は安価なモデルや決定論的ツールへ分けます。

重要な変更では `docs/16_blind_review_protocol.md` の **Discover first. Compare later.（先に独立して発見し、後から比較する）** を使います。一次レビューの結論を渡さず、仕様とソースから独立して挙動を再構築し、その後で両者の結果を照合します。

**メリット:** 確認バイアス、自己レビューの見落とし、複数AIが同じ前提から同じ誤りをする相関ミスを減らします。

## 標準スクリプト契約

このテンプレートを使うプロジェクトは、各言語・ビルドシステム固有のコマンドを、次の安定した「意図」に割り当てられます。

| Script | Intent |
| --- | --- |
| `doctor` | 環境確認 |
| `check` | 短時間のローカル検証 |
| `typecheck` | 型・静的チェック |
| `test` | unit / integration test |
| `build` | production build / package |
| `refactor:check` | 直列のrefactor gate |
| `release:check` | 直列のrelease / preflight gate |

これは全言語で同じ実装を要求するものではなく、「この名前は何を確認するか」を安定させる契約です。

## 実際に得られるメリット

このテンプレートを一貫して使うと、次を狙えます。

- **大規模リファクタリングの発生を減らす:** 一つの意味に一つの所有者、狭い責務、明示境界、変更局所性により、構造負債が広がる前に抑える。
- **人間が読みやすいコードになる:** ドメイン名、意味を持つ型、明示状態、理由を書くコメントにより、コードの意図が見える。
- **型・契約の変更が安全になる:** 型、単位、null可否、公開名、永続化形式、外部IFを「偶然の実装詳細」ではなく明示契約として扱う。
- **変更が小さくなる:** 既存挙動と設計意図を確認してから、本当に必要な差分だけを入れる。
- **コンテキスト・トークンを節約できる:** 全文読込ではなく索引・検索・短いJSON根拠を使う。
- **仕様ドリフトを減らせる:** 要件をGitHub上の仕様に固定し、矛盾時は実装側で補完せず仕様へ戻す。
- **再現可能性が上がる:** repository query、静的解析、テスト、gateを再実行できる。
- **AIコストを適切に配分できる:** 強い推論は設計・裁定へ、反復探索は決定論的ツールや低コスト処理へ分ける。
- **レビュー品質が上がる:** 変更行だけでなく影響実行経路を確認し、高リスク変更には本当に独立したblind reviewを追加できる。
- **refactor / releaseが安全になる:** 構造変更前に挙動を保護し、リスクに応じて検証範囲を広げる。
- **引継ぎと監査がしやすい:** 仕様、実装記録、コマンド、結果、判断、残存リスクが一つの会話や一人の記憶に依存しない。

## Quick Start

1. このリポジトリを新規プロジェクトのベースとして使う。
2. `AGENTS.md` を読む。
3. `docs/00_index.md` を読み、現在の作業に必要なカテゴリ・文書だけ開く。
4. 既存コードを変更する前に、現在の責務所有者、caller/consumer、契約、テスト、状態、失敗挙動を特定する。
5. 既存設計が許す範囲で、最小かつ局所的な実装にする。
6. プロジェクト固有ツールを標準スクリプト意図へ割り当てる。
7. repository discoveryが必要なら `docs/17_repo_index_and_query.md` に従い `python3 scripts/repo_query.py doctor` を実行する。
8. C/C++の意味解析・静的解析を使う場合は、実際のbuild configurationから正確な `compile_commands.json` を生成する。
9. 非自明な変更は `docs/specs/` に仕様を作り、`docs/19_chat_github_codex_workflow.md` の流れで実装する。
10. merge/release前に、実行した検証、未解決質問、人間確認点、残存リスクを正確に記録する。

ソースツリーと承認済み仕様が正本です。索引、生成された解析結果、実装記録、AI要約、過去レビューの結論は補助根拠であり、実際のリポジトリ状態や仕様契約を勝手に置き換えてはいけません。
